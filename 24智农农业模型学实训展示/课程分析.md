# 农业模型学实训课程安排不足分析

> 分析依据：51 份个人工作日志 + 1 份小组日志 + 1 份发布组B 实训总结报告
> 实训周期：2026年6月29日 — 7月2日（4天，每天8课时）
> 参与人数：55人，分5个功能组
> 项目基础：CN-strawberryDSSAT 系统（DSSAT 作物模型 Python 重构 + Docker 部署）

---

## 一、课程结构设计不足

### 1.1 第一天被工具安装吞噬，有效产出为零

第一天全部 8 课时消耗在 GitHub 注册、Trae 安装、Docker Desktop 配置上，没有任何专业产出。浦仕柏的统计显示环境配置类问题占比 43%，是最大时间消耗源。张广寻反映"第一天来老师就讲了几分钟然后让我们自己操作，感觉一头雾水"。杜国凤反映"面对庞大DSSAT代码库根本不知道从哪里开始，到最后才大概理清整个实训过程步骤"。

问题在于：课程设计者将工具学习和专业实操压缩在同一时段，工具学习成本直接挤压了专业训练时间。DSSAT 模型教学本身需要学生理解作物生理过程、Fortran 代码逻辑、Python 编程三个维度，这些认知负荷本应通过前置准备消化，而非占用宝贵的实训时间。

### 1.2 四天周期与项目复杂度严重不匹配

本项目涉及 DSSAT Fortran 作物模型解析、Python 代码重构与对齐、Docker 容器化部署、数据可视化、网页开发、项目汇报六大领域，任何一个领域单独拿出来都值得一周以上的深入学习。将如此复杂的项目压缩到四天，导致每个环节都只能浅尝辄止。

曹应东因"运行的模型太多，头脑开始乱了，没有办法继续想下去"而被迫停止工作，反映出任务密度超出了学生的认知承载能力。杨明珠指出"偏工具应用，对编程底层思维的训练涉及较少，任务拆解颗粒度偏粗"，说明课程在深度和广度之间的平衡存在偏差。

### 1.3 课时安排与考试季冲突

冯桂婷反映"上课时间过长，没有时间准备期末考试，很仓促，每天八节课，太多了"。实训安排在期末考试季前后，学生面临双重压力。连续两周每天8课时的高强度安排，导致下午时段精力普遍下降。陈思润承认"任务通常在早上就已经完成，导致下午存在松懈现象"，何梁宇反映"尤其下午会感到特别疲惫"。

## 二、任务分配机制不足

### 2.1 固定分组导致工作量严重不均

课程采用一次性固定分组方式，未考虑任务依赖关系和学生技能差异。直接后果是：部分学生过载（曹应东、董涵卓、翟翔宇连续高强度工作），部分学生闲置（至少17人明确反映有大量空闲玩手机时间）。

王俊翔揭示了一个结构性问题："组内大多人分配到的任务多为个人进行的任务，很少有团队任务，所以没事之后基本帮不上忙。能帮上忙的却又不了解其工作进度无法尽力帮助。"这表明任务设计缺乏协作维度，学生完成后无法横向支援。

### 2.2 串行依赖导致下游组大面积等待

科研组产出图表后发布组才能制作 PPT 和网页，但科研组参数调优持续到最后一天。解天蝶反映"得到代码的速度不够及时"导致空余时间无事可做。钟国富反映"还未接收到前端开发组所修改的代码，无法开展接下来的测试与部署"。陆温爽因"与发布组A 对接跟进不及时"错过图表后期修改环节。

课程设计未为存在依赖关系的下游组准备独立推进的备选任务，导致大量有效工时浪费在等待中。

### 2.3 任务颗粒度粗细不均

发布组B 网页优化组 3 人同做一项工作（段兴元反映"3个人优化网页人太多"），而科研组A 机理组 3 人承担了模型对齐的全部认知负荷。任务颗粒度差异巨大，从"上传文件到 GitHub"（钟名韩喻，半天完成）到"修改 17 次代码完成 8 项指标对齐"（翟翔宇，四天全力投入）跨度极大，缺乏统一的工作量评估标准。

## 三、教学指导不足

### 3.1 缺乏前置工具培训

全部 55 名学生中，绝大多数反映对 Trae、Docker、GitHub 三大工具完全没有前期接触。罗进萍指出"之前对 Trae 没有任何接触"。陈思润作为组长明确指出"本次项目前期未同步 Trae、Git 等工具完整操作手册，开发阶段大量工具疑问占用工时"。

课程设计中缺少工具预备环节，学生自学摸索耗时严重。不同学生掌握程度差异巨大，影响了协作效率。

### 3.2 缺乏模型机理讲解

课程直接让学生操作 DSSAT 模型代码，但未安排专门的模型机理讲解环节。杜国凤反映"面对庞大 DSSAT 代码库根本不知道从哪里开始"。杨明珠指出"偏工具应用，对编程底层思维的训练涉及较少"。

DSSAT 作物模型包含物候发育、光合作用、水分胁迫、呼吸作用、生物量分配、器官生长六大核心模块，每个模块都有复杂的物理意义和数学公式。学生不了解机理直接操作代码，导致只能依赖 AI 生成结果而不理解其原理。

### 3.3 AI 使用缺乏验证流程引导

多名学生反映过度依赖 AI 但缺乏验证能力。罗娅反映"AI 甚至可能为了迎合需求虚构数据。由于我自身缺少独立排查、核验问题的能力，只能完全依赖 AI"。蒋新林发现"AI 改变原代码导致后续结果错误"。袁芳馨承认"AI 生成出来的东西也没意识到要仔细核对修改，就草率地交了"。

课程设计中未包含"AI 生成 + 人工验证"的流程要求，学生将 AI 视为答案来源而非辅助工具，丧失了独立思考的动力。

## 四、资源准备不足

### 4.1 机房设备未提前配置

机房电脑未预装 Python 环境（numpy、numba 未安装，`D:\python\python.exe` 不存在），未预装 Git 工具，未预装 Docker Desktop（WSL 2 缺失导致闪退）。段兴元因机房电脑无法访问 GitHub 而几乎全程旁观。钟国富反映"电脑配置低，版本老，运行时间长出现过度发热，卡顿"。

课程设计中未包含设备验收环节，导致第一天大量时间消耗在排查环境问题上。

### 4.2 网络环境未优化

GitHub 443 端口超时导致超八成组员报错，教学进度滞后 40 分钟。保奇阳反映"各同学电脑配置不统一导致协助困难"。机房网络未配置代理或加速器，GitHub 访问成为瓶颈。

### 4.3 关键软件申请周期过长

Windows 可视化 DSSAT 面板申请周期约一周，无法在实训内完成安装。课程设计中未提前申请或准备替代方案，导致这一功能成为空缺。

---

## 五、协作机制设计不足

### 5.1 缺乏每日进度同步机制

杨艳鸿作为发布组B 组长反思最深刻："如果第一天就拉齐各组进度、设立每日同步机制，后期兵荒马乱完全可以避免。"课程设计中未安排每日晨会或进度同步环节，信息不对称导致大量返工。

科研组A 和科研组B 两位组长（陈思润、隋建炜）不约而同地自行建立了每日站会/复盘制度并取得了良好效果，证明这一机制的价值，但它是自发而非课程设计的。

### 5.2 跨组交付规范未提前约定

跨组交付文档未套用统一模板、格式杂乱，邓智予不得不"要求产出前先拉取最新模板，空白文档不予归档"。王俊翔反映"其他组个人日志记录不全、无具体问题报告汇总，导致跨组问题收集困难，只能线下逐个询问"。

### 5.3 关键交付物缺乏风险预案

Netlify 线上部署是核心交付目标，但课程设计中未准备备选方案。杨艳鸿反思"部署指导未能完全吃透"，发布组B 小组日志总结"项目后期缺乏 Plan B 的风险意识"。课程设计中未要求学生在第一天就确认部署方案和备选路径。

---

## 六、疲劳管理不足

### 6.1 连续高强度无休息间隔

连续两周每天8课时，下午时段精力普遍下降。杜国凤直言"一直盯着电脑屏幕有点怀疑人生，内心很想结束这个项目"。课程设计中未安排休息间隔，也未考虑将高强度认知任务与较轻松的文档整理任务交替安排。

### 6.2 任务量与精力曲线错配

陈思润验证了这一规律——"任务通常在早上就已经完成，导致下午存在松懈现象"。课程设计中未考虑学生的精力曲线，高强度认知任务（如模型参数调优）被均匀分布在全天，而非集中在精力充沛的上午时段。
